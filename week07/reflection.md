# Week 7 Reflection

The most useful lesson this week was learning to separate the acceptance of a transaction from all the work that happens afterwards. Before this, I would probably have made the API call the fraud check, ledger update, and notification services directly. That design looks simple, but one slow service can delay the customer response or cause the whole transaction request to fail. Publishing a payment event to SQS gives the API a durable hand-off point, while SNS can give independent consumers their own copy of a confirmed event. The transaction service no longer needs to know how quickly each consumer works.

Building the fraud scorer made the failure behaviour clearer. An SQS batch should report only the records that failed, otherwise valid transactions are retried and may be processed again. The dead-letter queue also belongs to SQS for this event source mapping, not to the Lambda function. I would now design the FinTrust payment path around explicit service contracts, idempotent consumers, visible retry rules, and a traceable request ID. That makes failures easier to isolate and allows each team to deploy and scale its service independently.
