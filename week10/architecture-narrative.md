# FinTrust Migration Execution Narrative

FinTrust uses six migration strategies because one treatment would not fit the whole estate. The application portfolio contains 285 applications: 43 Retire, 28 Retain, 14 Repurchase, 114 Rehost, 57 Replatform and 29 Refactor. Retiring unused reporting tools comes first because it removes cost without introducing migration risk. The SWIFT gateway and mainframe workloads remain on premises until their physical and regulatory dependencies change. Supported HR and procurement products move to subscription services. Stable internal applications use MGN for a quick Rehost, selected databases and application runtimes Replatform to managed services, and the fraud and onboarding platforms Refactor because they need event driven scaling.

The Oracle to Aurora PostgreSQL path is heterogeneous, so Schema Conversion Tool runs before Database Migration Service. SCT produces the converted schema and a list of procedures requiring manual work. DMS then uses Full Load plus Change Data Capture. This keeps Oracle available while existing rows move and new changes are applied. Cutover is allowed only while the task is running, source and target lag are each no more than 30 seconds, no tables are in error, validation has no failed records and the application team has completed its checks. The package blocks an accidental `start-replication` call unless the caller explicitly approves a full restart.

FinTrust evaluated a full DataSync transfer and selected a hybrid path for the 3 PB compliance archive. Snowball Edge Storage Optimised devices move the initial bulk data. DataSync transfers changed files until cutover, preserves the final audit trail and verifies the destination. The daytime limit is 500 Mbps so production traffic keeps most of the Direct Connect capacity. The overnight limit is 9,000 Mbps. EventBridge Scheduler invokes a small Lambda action to change the limit; it does not keep a function sleeping between schedules. TLS protects the transfer in transit, and the S3 destination uses a customer managed KMS key.

The migration database exposes stable SQL views for engineering and reporting. Operations use Python for live task status and controlled actions. Analysts use SQL views for repeatable joins and progress measures. QuickSight can sit above those views when stakeholders need trends and drill down. This separation keeps operational changes out of dashboards while giving every cutover an auditable record.
